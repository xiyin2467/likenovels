# 产品功能规划（MoSCoW）

> 功能来源：对标 GoodNovel（出海标杆）+ 借鉴 iReader 阅读内核。
> 优先级：**Must**=MVP 必须；**Should**=尽快补齐；**Could**=锦上添花；**Won't（本期不做）**=明确不做。

## 设计原则

- **MVP 只做 Must**：账号最小集 + 书库发现 + 阅读器 + 金币解锁/等待解锁/激励广告/充值 + 推送/归因/埋点 + 合规。
- **Should 在 MVP 后 1–2 个迭代补齐**。
- **Won't 项（社区/UGC/TTS/漫画/有声）明确本期不做**，避免过早复杂化（YAGNI）。

## APK 深度映射后的优先级调整

依据 `docs/research/APK深度架构映射.md`，功能优先级按以下原则收敛：

### MVP 必须更明确

- **搜索结果页**：GoodNovel 有 `SearchActivity`，搜索是用户主动找书入口，应从 Should 提升为 Must 的完整页面，而不是只保留输入框。
- **章节目录页**：GoodNovel 有 `ReaderCatalogActivity`，iReader 也有成熟目录/进度能力；目录应进入 MVP，支撑阅读器可用性。
- **钱包流水详情**：GoodNovel 有 `WalletHistoryActivity`、`ExpenseRecordActivity`，付费产品必须解释每一笔金币流向。
- **等待解锁提醒**：GoodNovel 有 `WaitUnlockListActivity`，等待解锁不只是付费墙按钮，还应有倒计时/提醒/列表入口。
- **语言与推送管理**：GoodNovel 有 `LanguageActivity`、`PushManagerActivity`，多语言和通知控制进入 MVP 合规基线。

### Should 保持但不要提前工程化

- **站内信/消息中心**：GoodNovel 有 Inbox/NotifyMessage，应做轻量消息页，但复杂活动消息系统可后置。
- **书评/评分**：GoodNovel 评论模块丰富，但 MVP 只做评分/书评入口和少量展示，社区互动延后。
- **批量解锁/自动解锁**：GoodNovel/iReader 均有类似能力，但会增加账务复杂度，先作为 V1.x 优化。

### 明确继续 Won't

- 作者中心/UGC、社区发帖/关注、漫画、有声/TTS/AI、复杂 Gems/兑换体系仍不进入 MVP。
- iReader 的国内支付、厂商推送、国内广告聚合、高风险权限、加固/插件化不进入任何海外版本规划。

### 对当前原型的映射要求

当前 `prototypes/v0-lofi/` 至少需要保留这些可点击入口：搜索结果、榜单详情、分类详情、章节目录、消息/通知、语言、推送管理、隐私、钱包流水、购买历史。它们用于验证信息架构，不代表 MVP 都要完整开发成生产功能。
