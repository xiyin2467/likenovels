### 1. GoodNovel 新发现

#### 1.1 App Links / Deeplink 体系（证据：`goodnovel_deep.json → intent_filters`）

- **自定义 scheme**：`sac091120e://`（神策 SDK scheme，用于推送/广告→App 精确跳转）
- **App Links（HTTPS）**：`https://ul3.goodnovel.com`（SplashActivity 接收，`BROWSABLE`+`DEFAULT`），说明 GoodNovel 已部署 App Links 来实现网页→App 无缝跳转，支撑买量落地页、分享链接直达书籍/章节。
- **Facebook Custom Tab**：`fbconnect://cct.com.read.goodnovel`，用于 Facebook 登录回调。
- **LoginDispatchActivity**：自定义 `action: android.intent.action.login`，说明登录流独立管理，支持多渠道（邮箱/Google/Facebook/Twitter）统一分发。

#### 1.2 Firebase 全家桶深度集成（证据：`goodnovel_deep.json → sdks`）

本次增强 SDK 检测新增确认：

- **Firebase Crashlytics**：崩溃监控。
- **Firebase Performance**：性能监控。
- 之前仅检测到"Firebase"笼统标签，本次拆分为 6 个子模块（Analytics/Performance/Messaging/Crashlytics/Remote Config/A/B Testing），说明 GoodNovel **重度依赖 Firebase 做数据驱动运营**。

### 2. iReader 新发现

#### 2.1 丰富的 Deeplink / Scheme 体系（证据：`ireader_deep.json → intent_filters`）

- **多 scheme 并存**：`ireader://`、`androidzhangyueireader://`、`zhangyueireader://`（三套），说明经历过 scheme 迁移但保持向后兼容。
- **丰富的 action**：
  - `SHOW_DETAIL` / `READ_BOOK` / `DOWNLOAD_BOOK` / `OPEN_URL` / `CATEGORY` / `SEARCH` / `READSHORTSTORY` / `SHOW_VIP`
  - 这些自定义 action 说明 iReader 的推送/活动能精准跳转到"书籍详情、直接阅读、下载、URL页、分类、搜索、短篇、VIP页"等具体场景。
- **文件类型关联**：注册了 epub/mobi/azw3/chm/umd/pdf/doc/docx/ppt/xls 等 20+ MIME 类型，是文件管理器点击直接用 iReader 打开的入口。

#### 2.2 插件化架构（证据：`ireader_deep.json → assets_categories → plugins_jars`）

iReader assets 中包含 **19 个内嵌 APK/JAR**：
- `pluginweb_bookbrowser.apk` — 阅读器插件
- `pluginweb_search.apk` — 搜索插件
- `pluginwebdiff_bookstore.apk` ~ `_bookstore5.apk` — 5 个书城插件（可能对应不同频道/实验版本）
- `pluginwebdiff_ad.apk` — 广告插件
- `pluginwebdiff_social.apk` — 社交插件
- `pluginwebdiff_video.apk` — 视频插件
- `pluginwebdiff_mine.apk` / `_personal.apk` — 个人中心插件
- `pluginwebdiff_group.apk` — 社区/群组插件
- `bdxadsdk.jar` — 百度广告 SDK
- `gdt_plugin/gdtadv2.jar` — 广点通广告 SDK

> 这说明 iReader 采用**重度插件化**架构（ZEUS 框架，见 meta-data 中 `ZEUS_PLUGIN_*`），将功能模块打包为独立 APK 按需加载。这在国内是常见做法（减包体/动态更新），但 **Google Play 不允许这种方式**，出海必须避免。

## 三、对后台（NestJS）推进的影响与注意事项

### 3.1 必须后端先行的功能

| 功能 | 为什么必须后端先行 | 表/接口预留 |
|---|---|---|
| **章节解锁账本** | 客户端不可自行判定"已解锁"（防刷），解锁扣币必须在服务端事务中完成，写入 `chapter_entitlement` + `wallet_ledger` | 已有设计（`后端API与数据模型.md`），需补充 **`idempotency_key` 索引**防重放 |
| **等待解锁调度** | `ready_at` 时间由服务端计算和校验，客户端不可篡改；到期后自动解锁需后台定时任务 | `wait_unlock` 表：`user_id`, `chapter_id`, `started_at`, `ready_at`, `status(pending/ready/claimed)` |
| **会员/订阅权益** | Google Play 订阅的 `purchase_token` 验证、续期/过期/退款 Webhook 处理、每日金币发放 | `subscription` 表：`user_id`, `plan(week/month/year)`, `purchase_token`, `expires_at`, `auto_renew`, `daily_coins_claimed_at` |
| **签到防刷** | 每日签到必须服务端校验时间、幂等、防重复领取 | `checkin_log` 表：`user_id`, `date(唯一)`, `coins`, `streak` |
| **Google Play Billing 验单** | 充值凭证必须在后端用 Google Play Developer API 验证，验证通过后才入账 | `payment_order.provider_token` 存储，调用 Google API `purchases.products.get` |
| **推送分群** | FCM topic 订阅或用户分群发送（追更提醒、等待解锁到期、运营活动）需要后端管理 token 和发送策略 | `push_token` 表 + `push_campaign` 表，预留 `user_segment` |
| **运营活动/H5 配置化** | 首充礼包、限时充值、赛事——不能写死在客户端，需要 CMS 下发 | `campaign` 表：`type`, `config_json`, `start_at`, `end_at`, `target_segment` |
| **AB 实验参数** | 付费墙位置/解锁单价/等待时长/广告频次 → Firebase Remote Config 或自有 AB 系统管理 | `experiment` 表或接入 Firebase Admin SDK |
| **退款与申诉** | Google Play 退款通知（RTDN）→ 后端 Webhook 接收 → 回收金币/标记用户 → 申诉工单 | `refund_log` 表；订阅的 `SUBSCRIPTION_REVOKED`/`SUBSCRIPTION_EXPIRED` 事件处理 |
| **内容审核/分级** | 书籍 age_rating 管理、举报处理、敏感词过滤 | `book.age_rating` 枚举扩展；`report` 表 |

### 3.2 表结构或接口上要预留什么

1. **`chapter_entitlement`**：
   - 增加 `idempotency_key`（唯一索引），防止网络重试导致重复扣币
   - 增加 `expires_at`（可选），为未来"限时解锁/会员到期回收"预留

2. **`wallet_ledger`**：
   - `type` 枚举扩展：除 `recharge/unlock/reward/checkin/refund` 外，预留 `subscription_daily`（会员每日金币）、`campaign`（活动奖励）、`bulk_unlock`（批量解锁）
   - `ref_type` + `ref_id` 组合引用，而非单一 `ref_id`

3. **`payment_order`**：
   - 预留 `is_first_purchase`（首充标记，首充礼包需要）
   - 预留 `campaign_id`（关联限时优惠活动）
   - 预留 `subscription_id`（关联订阅，区分一次性和续费）

4. **`user`**：
   - 预留 `vip_expires_at`（会员到期时间）
   - 预留 `referral_code` / `referred_by`（邀请体系）
   - 预留 `ab_group`（AB 分组标识，或用 Firebase 管理）

5. **推送相关**：
   - `push_token` 表：`user_id`, `platform(android/ios)`, `token`, `updated_at`
   - 图书追更关系：`book_follow` 表（或复用 `library_item`），用于新章推送

6. **运营活动**：
   - `campaign` 表：`id`, `type(first_purchase/limited_time/daily_task/checkin_streak)`, `config_json`, `start_at`, `end_at`
   - `user_campaign` 表：`user_id`, `campaign_id`, `status`, `claimed_at`

7. **API 版本化**：
   - 当前设计 `/api/v1` 正确，但需在 API Gateway 层预留 header `X-App-Version` 和 `X-AB-Group`，用于按客户端版本和实验组返回不同配置

### 3.3 合规注意点

#### GDPR / CCPA

- **数据删除**：`POST /me/delete` 必须**真删**（或 30 天内物理删除）所有 PII，包括：用户资料、阅读记录、支付记录中的关联、推送 token、归因数据中的设备 ID
- **数据导出**：GDPR 要求用户可导出其个人数据（Right to Data Portability），后端需提供 `/me/data-export` 端点
- **同意管理（CMP）**：首次启动需弹出 GDPR/CCPA 同意弹窗；未同意前不可初始化 AppsFlyer/Adjust/AdMob/Sensors 等 SDK
- **Firebase 配置**：`com.facebook.sdk.AutoLogAppEventsEnabled` 需在用户同意后才设为 true（GoodNovel 当前为 manifest 硬编码 true，可能有合规风险，我们应运行时控制）
- **AD_ID 权限**：Android 13+ 需显式声明 `com.google.android.gms.permission.AD_ID`，且需在隐私政策中说明用途

#### Google Play 政策

- **订阅管理**：必须在 App 内提供清晰的订阅管理入口（查看/取消），不能只跳转 Google Play
- **虚拟货币透明**：金币解锁价格需在购买前明确展示，不能模糊计价
- **退款处理**：Google Play 退款后（RTDN 通知），必须在 48 小时内回收对应权益，否则违规
- **内容政策**：女频小说含成人向/暴力内容需在商店信息中正确设置内容分级（IARC），App 内需年龄确认门
- **数据安全表单**：Google Play Console 需填写数据安全声明（收集哪些数据、是否加密传输、是否可删除），必须与实际行为一致
- **用户生成内容**：如开放评论/书评，需实现举报+审核机制，否则可能被下架

#### Apple App Store（iOS 预留）

- **虚拟货币**：App 内消费虚拟货币必须走 IAP，不能引导外部支付
- **订阅**：需实现 `StoreKit 2` 流程，提供恢复购买功能
- **Sign in with Apple**：如提供第三方登录则必须同时提供 Apple 登录
